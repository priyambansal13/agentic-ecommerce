# returns service

Return requests, evidence photos, the versioned refund policy (decision table R1–R9, pure `evaluatePolicy`) and refund cases with human approvals (dual control above ₹25,000: support then finance, never the same person) — the deterministic backbone of the governed refund agent. **Buyer:** `POST /v1/returns`, `GET /v1/returns/mine`, `GET /v1/returns/:id`, `POST /v1/returns/:id/evidence` (multipart `file`, JPEG/PNG/WebP ≤ 8 MB → WebP, EXIF stripped, perceptual hash → `reused_photo` signal), `POST /v1/returns/:id/appeal`, `GET /v1/evidence/:id/image?size=thumb|full`; public `GET /v1/refund-policy`. **Staff:** `GET /v1/refund-cases/queue?role=support|finance`, `GET /v1/refund-cases/:id`, `POST …/approve|reject` (support, finance, admin), `GET /v1/refund-cases/shadow-report` (admin). **Internal (agent):** `GET /v1/internal/refund-cases/:id/context`, `POST …/policy-eval` (scope `refunds:read`), `POST …/proposal`, `POST …/request-evidence` (`refunds:propose`), `POST …/execute` (`refunds:execute`) — accepted from tokens with realm role `service` OR exchanged agent tokens whose `act.sub` starts with `agent:` and that carry the scope; anything else gets 403. SHADOW proposals are stored only (visible to admin + shadow report); RECOMMEND/LIVE are shown to support; a LIVE proposal auto-approves only inside the server-re-evaluated envelope (R3) on a case no human has touched, with confidence ≥ 0.8. Default path while the agent runs in shadow: a new return is policy-checked by the service itself (returns-local risk heuristic) → hard rejects (outside the window) are `REJECTED` with an explanation (appealable), everything else `PENDING_HUMAN` for support. Refunds execute through payment `POST /v1/internal/refunds` (idempotent per case); `payment.refunded.v1` → `REFUNDED`. Replacement/store-credit outcomes close the case (replacement orders and the wallet are not built yet). Dashboards: `GET /v1/dashboard/buyer` (buyer), `/support` (support, admin), `/finance` (finance, admin — dual-control queue).
