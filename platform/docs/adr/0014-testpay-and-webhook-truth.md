# ADR 0014 — testpay test gateway, webhooks as payment truth, Stripe optional

- **Status:** Accepted (2026-10-24)
- **Related:** [02 §2.6](../02-lld.md#26-payment-service--ledger-payouts), [04 §4.2](../04-flows.md#42-checkout-saga--payment-strong-inventory-consistency), [10 §10.8](../10-marketplace.md)

## Context

P2 needs real checkout payments, but there are no Stripe or Razorpay keys yet, demos must run offline, and the
design rule is "payment truth = verified, deduped webhooks". A stub that flips a status directly would skip exactly
the parts that break in production: signature checks over the raw body, duplicate and out-of-order delivery,
captures arriving before the order data, late successes after an order was cancelled.

## Decision

1. Payments go through one provider interface. **`testpay`** is a built-in TEST gateway (always available, no real
   money): the buyer submits a test card on our pay page, and the gateway delivers a **signed webhook** to
   `POST /v1/webhooks/testpay` about 1 s later — sometimes twice (`TESTPAY_DUPLICATE_RATE`, default 0.25) — with
   the same `t=…,v1=HMAC-SHA256` scheme as Stripe. Test cards: `4242 4242 4242 4242` succeeds,
   `4000 0000 0000 0002` is declined, `4000 0000 0000 9995` has insufficient funds.
2. **Stripe** (test mode) is the same interface, enabled only when `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` and
   `STRIPE_PUBLISHABLE_KEY` are configured; the frontend then uses Stripe Elements with the session's client secret.
   **Razorpay** comes later behind the same interface.
3. **Webhooks are the only source of truth.** Every webhook is verified over the raw body (5-minute tolerance), stored
   in `webhook_events` keyed by `(provider, event id)` and processed in the same transaction as the payment status,
   the balanced ledger postings, the fee rows and the outbox event. Replays are 200 no-ops.
4. Ledger robustness: captures before `order.created.v1` go to `suspense:unallocated` and are allocated when the lines
   arrive; a success after `order.cancelled.v1` is captured and refunded automatically; cancellations of paid orders
   refund in full and reverse marketplace fees.
5. `TESTPAY_WEBHOOK_SECRET` is generated by the platform (`__generate__` in `.env.example`, per cluster in
   `ac k8s secrets`). Production can keep testpay for demos; a real launch disables it by removing the secret.

## Consequences

- The full payment path (signatures, dedupe, async truth, ledger) is exercised in every local run and demo, without
  external accounts. Switching to Stripe is configuration, not code.
- testpay is clearly labelled TEST everywhere (no real money); only brand + last 4 digits are stored.
- Processing webhooks synchronously (no BullMQ) keeps the design simple; if gateway timeouts become an issue,
  move processing behind the inbox table to a worker.
- Stripe has only been tested against mocked HTTP until keys are provided; refunds are recorded when the API call
  succeeds (no `charge.refunded` reconciliation yet).
